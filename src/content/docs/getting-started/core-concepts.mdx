## Two different shapes

| Package | Shape | Use it to |
| --- | --- | --- |
| `bf6-portal-mod-types` | One global namespace, `mod` | Type-check every call into the Portal engine |
| `bf6-portal-utils` | Many independent subpath modules | Reuse logging, UI, timers, events, and other helpers |

`mod` is not a module you import — it is declared globally once you add the
package to `tsconfig.json`'s `types`. Every Portal API call goes through it:

```ts
const isAlive = mod.GetSoldierState(player, mod.SoldierStateBool.IsAlive);
```

`bf6-portal-utils`, in contrast, is a real npm package with real imports.
Each module lives at its own subpath, with no barrel export:

```ts
import { Events } from "bf6-portal-utils/events";
import { Logger } from "bf6-portal-utils/logger";
```

## Only one handler per event, project-wide

Battlefield Portal itself enforces a hard rule: only one exported function
per event name (`OnPlayerDeployed`, `OngoingPlayer`, and so on) can exist in
a bundled project. `bf6-portal-utils/events` exists specifically to work
around this — it implements every event handler exactly once, internally,
and lets you subscribe to any event from anywhere in your code:

```ts title="src/mode.ts"
import { Events } from "bf6-portal-utils/events";

Events.OnPlayerDeployed.subscribe((eventPlayer: mod.Player) => {
  mod.DisplayNotificationMessage(mod.Message("Welcome to the match!"), eventPlayer);
});
```

:::caution
Once you use Events, or any module that depends on it (Logger, UI, and
Multi-Click Detector all do), do not also export your own `OnPlayerDeployed`
or similar handler function elsewhere in your project. The two mechanisms
will conflict — only one can actually run.
:::

:::caution
`Ongoing*` events (`OngoingPlayer`, and similar) fire up to 30 times per
second per player. Keep subscribed handlers fast and avoid allocating large
objects inside them.
:::
